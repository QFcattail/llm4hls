\title{Budgeted End-to-End LLM4HLS Agent: \\
Automated Repair and Optimization of Vitis HLS Code \\
within Constrained Tool-Call Budgets}

\author{
\IEEEauthorblockN{Anonymous}
\IEEEauthorblockA{Submitted to FPT'26 Design Competition -- Track A: LLM4HLS Agent}
}

\maketitle

\begin{abstract}
We present an autonomous AI agent that repairs and optimizes AMD Vitis HLS C/C++ kernels under a constrained tool-invocation budget. The agent receives an HLS task---possibly containing a functional bug, a synthesis failure, a co-simulation deadlock, or merely an unoptimized baseline---and iteratively drives it to functional correctness before optimizing its PPA (Performance--Power--Area). The architecture follows a linear-with-backtracking three-stage flow: \emph{correctness repair} $\rightarrow$ \emph{synthesis verification} $\rightarrow$ \emph{PPA optimization}, where every code edit re-verifies already-passed stages and a monotone checkpoint archive provides rollback for free. The optimization stage implements the AMD LLM4HLS four-phase workflow: design-brief extraction, strategy proposal with compatibility annotations, a reviewer-AI dual-confirmation gate, and combined code generation. A deterministic mechanical-check gate complements LLM self-review to catch signature changes that the LLM misses. We evaluate on six tasks spanning three task types (repair, structural, optimize) on Vitis 2025.2 targeting Alveo U55C at 200\,MHz with all three competition-recommended open-weight models (DeepSeek V4 Pro, Qwen3.5 122B, Qwen3.6 27B): every model clears the csim correctness gate on all six tasks (18/18), demonstrating that the architecture transfers across models without modification. With DeepSeek V4 Pro the agent achieves two perfect scores and up to 205$\times$ latency reduction; all candidates close timing with conservative Fmax of 200--353\,MHz at a maximum resource utilization of 3.5\%. A graded token-mode A/B study shows 8--31\% token savings without score degradation. All artifacts are packaged as a reproducible Docker image, and all experiment data are archived for auditability.
\end{abstract}

High-Level Synthesis, LLM agents, Vitis HLS, FPGA, correctness-first optimization, budgeted tool use

% ============================================================
\section{Introduction}
% ============================================================

High-Level Synthesis (HLS) compiles C/C++ into FPGA RTL, but writing correct HLS code requires simultaneously managing algorithm correctness and hardware constraints: a misplaced \texttt{\#pragma} can cause synthesis failure, co-simulation deadlock, or resource explosion. One-shot LLM prompting rarely succeeds; an iterative loop with tool feedback is necessary~\cite{react,autochip,hlsrepair}. FPT'26 Track A formalizes this problem~\cite{fpt26rules}: under a bounded tool-call budget, the agent must interpret the task, generate/modify HLS C/C++ code with pragmas, invoke metered tool feedback (csim/synth/cosim), parse logs for diagnosis, prioritize correctness over PPA, and terminate within budget---targeting Alveo U55C on Vitis 2025.2 with open-source models, with \emph{token consumption an explicit evaluation factor}.

Our contributions (details in Appendices~\ref{app:algo}--\ref{app:discussion}):
\begin{itemize}
    \item A \textbf{linear-with-backtracking three-stage architecture} (correctness $\rightarrow$ synth $\rightarrow$ optimize) where every edit re-verifies passed stages and a monotone checkpoint archive gives rollback for free (\S\ref{sec:arch}).
    \item An \textbf{autonomous implementation of the AMD LLM4HLS four-phase optimization workflow}~\cite{amdllm4hls}---design-brief extraction, strategy proposal, reviewer-AI dual-confirmation, combined application (\S\ref{sec:algo}).
    \item A \textbf{dual-gate review} pairing deterministic mechanical checks (signature/header) with LLM self-review, catching the signature-change blind spot of LLM self-check (\S\ref{sec:algo}).
    \item A \textbf{graded token-saving switch} saving 8--31\% tokens without score loss in an A/B study (App.~\ref{sec:tokens}).
    \item \textbf{Multi-model, full-PPA validation} on six tasks with the three competition-recommended open-weight models, plus a run-to-run variance analysis (\S\ref{sec:results}).
\end{itemize}

% ============================================================
\section{Evaluation Model and Contest Rules}
\label{sec:eval}
% ============================================================

Every design decision is grounded in the evaluation model of the official harness~\cite{fpt26rules}, which exposes three budget-charged calls: \texttt{csim(code)} (1 credit), \texttt{synth(code)} (4 credits), \texttt{cosim(code)} (20 credits), each returning a structured pass/error phase and appended to an audit transcript. The agent supplies only the kernel source; headers and testbenches are fixed by the harness. Scoring uses a hidden testbench, run \emph{outside} the agent's budget, with a correctness gate:
\begin{equation}
\label{eq:score}
\text{score} = \begin{cases}
0 & \text{if not functional\_pass} \\
\text{diff} \times (0.5\,c + 0.2\,s + 0.3\,p) & \text{otherwise}
\end{cases}
\end{equation}
where $c=1$ if hidden csim (+ cosim if required) passes, $s=1$ if synthesizable, and $p = \min(\text{Accel}, 8)/8$ with $\text{Accel} = \text{baseline\_lat} / \text{cand\_lat}$. Correctness is a hard 0.5-weight gate, synthesis adds 0.2, and latency-only acceleration (capped at 8$\times$) adds 0.3---dictating a \emph{correctness-first} strategy (metric implications analyzed in App.~\ref{app:discussion}).

Two independent budgets matter. \textbf{Credit} (tool calls) is a \emph{hard} limit---exceeding it stops the agent---and does not accumulate across tasks, so ``go linearly, retry on failure, stop when exhausted'' is score-equivalent to any clever early-stopping strategy. \textbf{Token} (LLM consumption) is a \emph{soft} limit but an explicit final-evaluation factor, so token savings have real value while credit savings do not. Agent intelligence therefore focuses on \emph{making each step pass on the first try} (fewer retries $\to$ fewer tokens), not on deciding \emph{when} to stop. The harness defines four task types (repair, optimize, structural, generate); our suite covers the first three (App.~\ref{app:exp}).

\section{System Architecture}
\label{sec:arch}
% ============================================================

The agent follows a \emph{linear flow with backtracking re-verification and checkpoint arbitration} (Fig.~\ref{fig:overview}): the main flow is correctness $\rightarrow$ synth $\rightarrow$ optimize, but every code edit re-verifies already-passed stages---fixing a later bug can break an earlier one---and a monotone checkpoint archive provides rollback for free. The design instantiates the ReAct reasoning--acting loop~\cite{react} in the HLS domain: LLM calls produce reasoning + candidate code, and metered tool calls return structured observations. A zero-cost router reads only \texttt{task.toml} to set the correctness gates (csim, or csim+cosim for structural tasks). The checkpoint maps stage completion to monotone levels (Lv1 = correctness passed, worth $0.5\times$diff; Lv2 = +synth, $+0.2\times$diff) and admits a candidate only if it levels up, or matches the level with strictly lower latency---the archive never regresses, so a failed candidate simply never replaces the best (full router/checkpoint rules: App.~\ref{app:algo}).

\section{Core Algorithms}
\label{sec:algo}
% ============================================================

\textbf{Stage 1 (correctness repair)} runs a review--csim--repair loop: a pre-csim LLM review fixes obvious bugs before spending credits (on \texttt{residual}, it fixed the DATAFLOW deadlock \emph{before} any tool call); on failure, feedback is distilled, KB-matched, repaired, and passed through a \emph{dual gate}---deterministic signature/include checks plus LLM self-review---before retry. \textbf{Stage 2 (synthesis verification)} checks synthesizability and baseline latency; each synth-repair edit re-verifies csim (1 credit) before re-synthesizing (4 credits), and a latency-validity defense rejects 0-cycle parse anomalies. \textbf{Stage 3 (PPA optimization)} implements the AMD four-phase workflow~\cite{amdllm4hls}: design-brief extraction, strategy proposal with compatibility annotations, a reviewer-AI dual-confirmation gate, and combined application; a credit-driven stopping policy halts on convergence or budget exhaustion, reserving credits on structural tasks for a final cosim re-check that repairs, or rolls back, the optimized code (full stage details, stopping policy, and re-check rules: App.~\ref{app:algo}).

\subsection{Setup}

All runs execute real (non-mocked) Vitis 2025.2 csim/synth/cosim~\cite{ug1399} on an Ubuntu 22.04 server, targeting Alveo U55C (\texttt{xcu55c-fsvh2892-2L-e}) at 200\,MHz (5\,ns), with SCOREs computed by the official \texttt{grade()} on hidden testbenches outside the agent budget. We evaluate the three contest-recommended open-weight models~\cite{fpt26rules,deepseek,qwen}---DeepSeek V4 Pro (official API), Qwen3.5 122B A10B, and Qwen3.6 27B---at temperature 0.2 with token-mode \texttt{full} unless stated. The suite spans six tasks: three official public tasks (projection/repair/diff.\ 2, residual/structural/4, dotProduct/optimize/3) and three self-built optimize tasks in official format with hidden testbenches (matmul/3, fir/2, vecadd/1). Full setup, task tables, and archived artifacts: App.~\ref{app:exp}.

\subsection{Token Efficiency and Run Variance}

A graded \texttt{-{}-token-mode} switch controlling reasoning effort saves 8--31\% tokens (mean 22.7\%) with no score degradation in an A/B study; \texttt{balanced} mode is the recommended default (App.~\ref{sec:tokens}). Across 15 archived repeat runs, correctness is stable in 15/15---variance is confined to optimization quality (App.~\ref{app:exp}); case studies for dotProduct, residual, and projection are in App.~\ref{app:cases}.

\section{Related Work}
% ============================================================

ReAct~\cite{react} interleaves reasoning traces with environment actions and SWE-agent~\cite{sweagent} shows the agent--computer interface materially affects performance; following Anthropic's agent guidance~\cite{anthropicagents}, our agent is deliberately a simple, composable \emph{workflow} with LLM steps, not a free-running planner. Among LLM hardware-design systems (AutoChip~\cite{autochip}, RTLFixer~\cite{rtlfixer}, HLS-Repair~\cite{hlsrepair}, HLSPilot~\cite{hlspilot}) we are closest to HLS-Repair and HLSPilot but differ by operating under a \emph{hard tool-call budget}, coupling repair with \emph{PPA optimization} end-to-end, and using a monotone score-aligned checkpoint. AMD's LLM4HLS case study~\cite{amdllm4hls} proposes a human-in-the-loop four-phase workflow and names pragma interaction as a key LLM weakness; we engineer it into a fully autonomous loop with a reviewer-AI dual-confirmation gate plus deterministic mechanical checks.

% ============================================================
\section{Conclusion}
% ============================================================

Under constrained tool-call budgets, our agent repaired and optimized Vitis HLS code across six tasks and three task types, achieving a 100\% correctness pass rate with all three competition-recommended open-weight models (18/18 csim gates). With DeepSeek V4 Pro it achieved two perfect scores and up to 205$\times$ latency reduction, with all candidates closing timing (Fmax 200--353\,MHz) at $\leq$3.5\% resource utilization, while a balanced token mode saves $\sim$23\% tokens at no score cost. The full system, prompts, logs, and a reproducible Docker image accompany this report (App.~\ref{app:repro}); per-task details, case studies, and discussions are in the appendices.

\section{Reproduction, Observability, and Docker}
\label{app:repro}
% ============================================================

\paragraph{Docker.} The contest requires submissions to build and run in Docker. We provide a \texttt{Dockerfile} and \texttt{docker-run.sh}:
\begin{itemize}
    \item \textbf{Image contents}: Ubuntu 22.04 + official \texttt{vitis.dockerfile} dependency layer + Python 3.12 venv + textual/rich (TUI) + agent source + harness. \emph{Vitis itself is not baked in} ($\sim$92\,GB + license-bound); it is read-only mounted from the host at runtime.
    \item \textbf{Key finding}: Vitis \texttt{settings64.sh} hard-codes sibling-directory absolute paths (DocNav/Vivado/Model\_Composer). The \emph{entire} Xilinx tree must be mounted to the \emph{same path} in the container (not remapped to \texttt{/opt/xilinx})---this matches the official \texttt{run-vitis.sh} model.
\end{itemize}
On the server, \texttt{docker build} succeeded, and in-container runs reproduced host results: projection (SCORE 1.400) and dotProduct (SCORE 3.000), with actual csim/synth execution.

\paragraph{Commands.}
\begin{footnotesize}
\begin{verbatim}
# 1. Build image (host needs Vitis 2025.2)
docker build -t fpga-agent:0.7.4 .

# 2. Run a task (scripted backend, no tokens)
./docker-run.sh \
    contest/fpt26-harness/tasks/projection_bugfix

# 3. Real LLM run (needs API key in .env)
./docker-run.sh \
    contest/fpt26-harness/tasks/dotProduct_optimize \
    --backend deepseek

# 4. Model selection via env overrides (OpenAI-compatible)
LLM_BASE_URL=<endpoint> LLM_MODEL=qwen3.6-27b \
LLM_THINKING=enable_thinking \
python3 scripts/run_agent.py <task_dir> --backend deepseek
\end{verbatim}
\end{footnotesize}

\paragraph{Observability.} Each run produces three layers of logs, all archived under \texttt{experiments/}: (1) a JSONL event log (route, tool\_result, mechanical\_review, review, checkpoint, llm\_call, strategy\_select, optimize\_discard, submit), analyzable with \texttt{jq}; (2) a verbatim prompt log (full system/user prompt + response for every LLM call); (3) a score history (\texttt{scores.jsonl}) of cross-run SCORE/latency/credits/tokens trends. A heartbeat thread writes a heartbeat event every 10\,s (stage/age/credit\_remaining) for stall detection---Vitis cosim can run 15 minutes, and the heartbeat confirms the process is alive.

\paragraph{TUI dashboard.} For interactive use, the agent ships a Textual/Rich terminal dashboard with four regions: a five-stage flow chart with live status glyphs and per-stage stats; a tool-error bar (gcc-style \texttt{file:line: error:}, Vitis \texttt{[SIM 211-2]} codes) that doubles as a strategy panel during optimization; a streaming LLM output panel (chain-of-thought in dim italic, C++ syntax-highlighted code); and a status bar with credit progress, cumulative tokens (with reasoning breakdown), and last review verdict. \section{Architecture and Algorithm Details}
\label{app:algo}
% ============================================================

\subsection{Router}

The router runs once at entry at zero credit cost, reading only \texttt{task.toml}:
\begin{itemize}
    \item \texttt{requires\_cosim=true} (structural) $\to$ correctness stages = [csim, cosim]; otherwise [csim].
    \item \texttt{task\_type=optimize} $\to$ initial\_level=1 (assume csim passes; the loop confirms it); otherwise 0.
    \item All types set \texttt{needs\_optimize=True}; the main loop decides post-synth whether optimization is reachable.
\end{itemize}

\subsection{Checkpoint Logic}
\label{sec:checkpoint}

The checkpoint is the core data structure, mapping stage completion to a monotone level:

\begin{itemize}
    \item \textbf{Lv0}: nothing passed $\to$ 0 points.
    \item \textbf{Lv1}: csim passes (+ cosim if structural) $\to$ 0.5$\times$diff.
    \item \textbf{Lv2}: Lv1 + synth passes $\to$ +0.2$\times$diff; latency available for PPA.
\end{itemize}

\textbf{Three archive rules} (candidate $C$ vs.\ current best $B$):
\begin{enumerate}
    \item $\text{level}(C) > \text{level}(B)$ $\to$ always accept $C$.
    \item $\text{level}(C) = \text{level}(B)$ $\to$ accept $C$ only if its latency is strictly lower.
    \item $\text{level}(C) < \text{level}(B)$ $\to$ never accept (correctness regression).
\end{enumerate}

The archive only moves forward (monotone non-decreasing level). A failed candidate that broke an earlier stage simply never enters the archive---\emph{best} stays at the last verified version, yielding automatic rollback with no extra logic.

\subsection{Stage 1: Correctness Repair Loop}
\label{sec:correctness}

Goal: pass all correctness-gate stages. Each iteration:

\begin{enumerate}
    \item \textbf{Pre-csim LLM review} (first attempt only): before spending a credit on csim, let the LLM inspect the code and fix obvious bugs. On the \texttt{residual\_stream\_deadlock} task, this step identified and fixed the DATAFLOW deadlock pattern \emph{before} any tool call---saving a 20-credit failed cosim and a 15-minute timeout.
    \item Run csim (+ cosim if structural).
    \item Pass $\to$ archive to Lv1, proceed to Stage 2.
    \item Fail $\to$ distill feedback $\to$ KB retrieval $\to$ repair $\to$ dual-gate review $\to$ retry.
\end{enumerate}

\textbf{Dual-gate review} (applied at every code edit):
\begin{itemize}
    \item \emph{Gate 1 -- Mechanical checks} (deterministic, non-LLM): verify the top-level function signature is unchanged and the header \texttt{\#include} is still present. In one observed instance, the LLM self-check approved a candidate whose top-level signature had changed (which would fail hidden-testbench linking); the mechanical gate caught it. We therefore keep the deterministic gate as a hard precondition.
    \item \emph{Gate 2 -- LLM self-check review}: same model, reviewer prompt, checking interface/new bugs/pragma hazards. A rejection triggers re-generation.
\end{itemize}

\subsection{Stage 2: Synthesis Verification}

Goal: verify synthesizability and obtain baseline latency.

On synth failure, a repair loop (isomorphic to Stage 1) runs, but \emph{each edit re-verifies csim (1 credit) before spending another synth (4 credits)}---fixing synth can break correctness, so the cheap csim confirms no regression first. The loop runs up to \texttt{max\_synth\_rounds}=3 repair attempts (a bounded budget: each round costs at most csim 1 + synth 4 = 5 credits, so 3 rounds $\leq$ 15 credits, gated by \texttt{can\_afford} checks).

\textbf{Latency validity defense}: the machine once produced a synth pass with latency=0 (a parse anomaly). \texttt{\_valid\_latency()} treats $\leq 0$ as missing data, preventing a ``0-cycle'' design from winning every same-level comparison and corrupting the archive.

\subsection{Stage 3: PPA Optimization --- AMD Four-Phase Workflow}
\label{sec:optimize}

This stage implements the AMD LLM4HLS four-phase methodology~\cite{amdllm4hls}:

\paragraph{Phase 1 -- Context Loading.}
\begin{itemize}
    \item Official design document (interface contract + headers, preventing interface-breaking optimizations).
    \item \emph{Design brief extraction} (\texttt{extract\_design\_brief}, LLM\#3, first round only, cached): the LLM distills the kernel's functionality, loop structure, dataflow, and bottleneck hypothesis. AMD's key insight: ``without design context, the LLM gives only generic advice.''
    \item Synthesis report (latency/II/resources).
    \item Device constraints (U55C @ 200\,MHz).
    \item Checkpoint snapshot (for \S\ref{sec:cosim-recheck} rollback).
\end{itemize}

\paragraph{Phase 2a -- Strategy Proposal (\texttt{propose\_strategies}, LLM\#4).}
Injects design document + brief + synth report; proposes 2--4 strategies, each annotated with \texttt{combinable\_with} (which other strategies it does not interfere with). Uses JSON structured output.

\paragraph{Phase 2b -- Reviewer AI (\texttt{select\_strategies}, LLM\#5).}
A self-check (same model, reviewer prompt) performing \emph{two steps}:
\begin{enumerate}
    \item \textbf{Feasibility review}: for each strategy, judge whether the \emph{plan itself} is sound---interface unchanged, functionality preserved, synthesizable, resources fit. Poisoned plans are rejected with a reason (recorded in the \texttt{rejected} list).
    \item \textbf{Compatibility re-check}: pick a compatible subset from the surviving strategies.
\end{enumerate}
\textbf{Dual-confirmation rule}: the \emph{proposer} and the \emph{reviewer} must both agree the strategies do not interfere before the code-generation AI may combine them. This targets pragma interaction---AMD's named LLM weakness.

\paragraph{Phase 3 -- Combined Application (\texttt{apply\_strategies}, LLM\#6).}
The selected subset is applied as one candidate (single strategy = $N{=}1$ special case), passing the dual-gate review, then re-verifying csim + synth.

\textbf{Same-level arbitration}: synth passes and latency $<$ best $\to$ update archive; otherwise discard.

\textbf{Failure handling}:
\begin{itemize}
    \item Single-strategy candidate fails csim/synth $\to$ repair loop (inject failure feedback + KB hits, up to 3 retries).
    \item Multi-strategy (combo) candidate fails $\to$ \emph{combo-attribution fallback}: retry with the subset's first strategy alone (injecting failure feedback so the LLM avoids repeating the mistake).
\end{itemize}

\subsection{Stopping Policy}

Credit-driven, not a fixed round cap:
\begin{itemize}
    \item \emph{Convergence}: a candidate that passes csim+synth but is not strictly faster than the archive (latency $\geq$ best) is treated as convergence---optimization stops.
    \item \emph{Credit exhaustion (no cosim required)}: keep optimizing until one csim + one synth can no longer be afforded.
    \item \emph{Credit reservation (cosim required)}: for structural tasks, stop early enough to reserve 26 credits (1 cosim + 1 csim + 1 synth + 1 repair csim) for the final RTL re-check (\S\ref{sec:cosim-recheck}), so a cosim failure can be repaired rather than forcing an immediate rollback.
    \item A safety round cap (default 20) prevents pathological infinite loops but is not the primary stopping condition.
\end{itemize}

\subsection{Post-Optimization Co-Simulation Re-check}
\label{sec:cosim-recheck}

After optimization changes the code, a final RTL-level sanity check runs for \emph{all} task types---the synth report is a static estimate, not a measured value (e.g., \texttt{residual} estimated 68 vs.\ measured 97 cycles). If best changed during optimization and cosim is affordable, cosim runs:
\begin{itemize}
    \item Pass $\to$ mark \texttt{cosim\_ok}.
    \item Fail $\to$ \emph{repair-then-rollback}: the agent first attempts to repair the final optimized version (injecting the cosim failure feedback + KB hits into a review-gated repair, then re-verifying csim + cosim, up to 3 retries). Only when the repair budget is exhausted does it roll back to the pre-optimization snapshot. This preserves optimized latency when possible rather than discarding it wholesale.
    \item Structural task with insufficient budget for cosim $\to$ rollback to the pre-optimization snapshot (verified code must not be shipped without an RTL check).
\end{itemize}

\subsection{Cross-Model Analysis}

Three observations emerge from the cross-model data (Table~\ref{tab:multimodel}).

\paragraph{Correctness transfers; optimization does not.} All three models cleared the csim correctness gate on all six tasks (18/18), and two of three passed synthesis everywhere---the correctness-first architecture (dual gate + monotone checkpoint) is model-agnostic. Optimization quality, by contrast, is neither monotone in model size nor consistent across tasks: Qwen3.6 27B, the smallest model, produced the \emph{only} perfect matmul (210$\times$, capped) while DeepSeek V4 Pro stalled at 5.25$\times$ on the same task; conversely Qwen3.6 left vecadd essentially unoptimized (latency identical to baseline) where both larger models reached the score cap.

\paragraph{Model behavior differs in failure mode, not just degree.} Qwen3.5 122B's two sub-par results expose distinct failure modes. On vecadd, its candidate timed out in synthesis four consecutive times (600\,s limit), exhausting the budget at SCORE 0.5---the agent lacks a ``back off to a simpler design'' reflex for synth timeouts. On matmul, its reviewer AI twice rejected the \emph{unmodified, known-correct baseline} during the pre-csim review and applied a ``fix'' that doubled latency (32,827 vs.\ 16,422 cycles) before the checkpoint anchored; the archive then faithfully optimized from a corrupted starting point. This failure mode---an overzealous reviewer mutating a good baseline before anchoring---was invisible in our single-model testing and motivates anchoring the archive on the unmodified baseline (future work).

\paragraph{Token cost is not monotone in model size.} Total tokens: Qwen3.6 277k $<$ DeepSeek 373k $<$ Qwen3.5 409k. The 122B model is the most expensive per task (fir: 152k tokens) because its long reasoning chains fire on every call, while DeepSeek achieves the best score-per-token on the hardest task (residual 4.000 at 77.8k tokens). For a budget-conscious submission, DeepSeek V4 Pro offers the best score/token trade-off; Qwen3.6 27B is a viable low-cost option when paired with stronger optimization guidance. Across all 17 synthesizable candidates (all models), timing is met with conservative Fmax 200--353\,MHz; per-run synthesis reports (latency/resources/timing) are archived as \texttt{ppa.json} in the submission's \texttt{experiments/} directory.

\section{Case Studies}
\label{app:cases}

\subsection{dotProduct (Optimize, Perfect Score)}

\begin{figure}[t]
\centering
\begin{lstlisting}[caption={Optimized dotProduct kernel: cyclic array partition + pipelined tiled loop (51.35$\times$ acceleration).},label={lst:dotproduct}]
#include "dotProduct.h"
FeatureType dotProduct(
    FeatureType param[NUM_FEATURES],
    DataType feature[NUM_FEATURES]) {
  const int unroll_factor = PAR_FACTOR;
#pragma HLS array_partition variable=param \
        cyclic factor=unroll_factor
#pragma HLS array_partition variable=feature \
        cyclic factor=unroll_factor
  FeatureType result = 0;
DOT:
  for (int i = 0; i < NUM_FEATURES/PAR_FACTOR; i++) {
#pragma HLS PIPELINE II=1
  DOT_INNER:
    for (int j = 0; j < PAR_FACTOR; j++)
      result += param[i*PAR_FACTOR+j]
              * feature[i*PAR_FACTOR+j];
  }
  return result;
}
\end{lstlisting}
\end{figure}

The optimization loop reduced latency from 73 to 20 cycles over 4 rounds (3 effective + 1 convergence stop). The reviewer AI rejected two hazardous proposals: ``Full Unroll to 1024 Lanes'' (resource explosion) and ``Increase to 128'' (conflicts with existing partition pragmas)---in this run, feasibility review prevented two likely-failing candidates, each of which would have cost csim+synth credits and repair tokens.

\paragraph{Transcript excerpt:}
\begin{footnotesize}
\begin{verbatim}
#1 [csim]  pass       [1/40]  correctness confirmed
#2 [synth] pass lat=73[5/40]  baseline
    >> ENTER optimize
    R1: adder tree per chunk    -> 73->36 (accept)
    R2: parallelism 64 lanes    -> 36->20 (accept)
    R3: decouple chunk accum.   -> 22     (discard)
    opt-STOP, best=20
#9 [cosim] pass lat=18[40/40]  RTL sanity check passed
    SUBMIT: SCORE 3.000
\end{verbatim}
\end{footnotesize}

\subsection{residual (Structural, Cosim Deadlock Repair)}

This is the hardest task (difficulty 4). A DATAFLOW skip/residual connection has the producer write its entire main stream before the skip stream. C-simulation's unbounded FIFOs hide the problem, but co-simulation's depth-2 bounded FIFOs cannot buffer the burst, causing deadlock.

The agent's pre-csim LLM review identified and fixed this pattern \emph{before} spending any cosim credit. Over 4 optimization rounds, latency dropped from 68 to 10 cycles, and the post-optimization cosim re-check passed, achieving a perfect 4.000. The three archived runs (Table~\ref{tab:variance}) all repaired the deadlock on the first attempt; they differ only in optimization depth.

\subsection{projection (Repair, Minimal Flow)}

The bug was a dropped vertex term in the \texttt{angle==0} branch:
\begin{footnotesize}
\begin{verbatim}
// BUG:   z = z0/3 + z1/3;        // drops z2
// FIXED: z = z0/3 + z1/3 + z2/3; // all three
\end{verbatim}
\end{footnotesize}
The pre-csim review caught this before the first csim credit was spent. The entire run used only 5 credits and 3,629 tokens. Interestingly, on the same task Qwen3.6 27B's reviewer AI twice rejected its own repair candidates for a robustness issue the original code never handled (no default branch for \texttt{angle==3} in the \texttt{bit2} range) before accepting a hardened version---the dual gate enforces defensive coding even on a minimal repair, at the cost of extra reasoning tokens (13,896 vs.\ DeepSeek's 3,629).

\subsection{Why Latency-First PPA Is Score-Optimal (and Its Limits)}
\label{sec:ppa-discussion}

A natural criticism of our agent is that its optimization objective considers only \emph{latency}, not the full PPA triad. This is a deliberate alignment with the official metric, not an oversight: the scored PPA term in Eq.~\eqref{eq:score} is $p=\min(\text{baseline\_lat}/\text{cand\_lat},\,8)/8$---area and power do not enter the score at all. Under this metric, the marginal value of area or power reduction is exactly zero, while latency reduction is worth up to $0.3\times\text{diff}$; spending credits on anything but latency after Lv2 would be score-irrational.

We nevertheless guard against the two ways a latency-only objective can produce a bad design:
\begin{enumerate}
    \item \emph{Area explosion}: the reviewer-AI feasibility gate rejects resource-explosion proposals before they consume credits (observed: ``Full Unroll to 1024 Lanes'' rejected on dotProduct). Table~\ref{tab:ppa} confirms the outcome empirically: utilization $\leq$3.5\% on all tasks.
    \item \emph{Timing failure}: every submitted candidate must pass synthesis at the 5\,ns target; Table~\ref{tab:ppa} shows conservative Fmax of 200--353\,MHz, comfortably above the 100\,MHz rule.
\end{enumerate}

Were the metric to score area and power (e.g., $p = w_l \hat{l} + w_a \hat{a} + w_p \hat{p}$ with normalized terms), the strategy space would need multi-objective arbitration at the same-level checkpoint rule (rule 2 currently compares latency only). A principled weight allocation under the \emph{current} formula is: correctness first (0.5, hard gate), then synth (0.2, nearly free once correct), then latency up to the 8$\times$ cap (0.3), and nothing else. We report full PPA for transparency and as a basis for future area/power-aware objectives.

\subsection{A Harness Edge Case: Zero Latency}
\label{sec:harness-quirk}

The projection kernel synthesizes to combinational logic (latency 0). The official scorer computes acceleration only \texttt{if cand\_lat and base\_lat:}---0 is falsy in Python---so a latency-0 design forfeits the entire 0.3 PPA slice regardless of its actual speed, capping projection's score at $2\times0.7=1.400$. We report this as an observation for the benchmark maintainers: arguably a perfect combinational design deserves the PPA slice, and the condition should test \texttt{is not None}.

\subsection{Limitations}
\label{sec:limitations}

\begin{enumerate}
    \item \textbf{Single-run protocol per (model, task)}: budget constraints allowed one run per pair for the two Qwen models; Table~\ref{tab:variance} quantifies DeepSeek variance, but cross-model conclusions should be read as indicative, not statistical.
    \item \textbf{Pre-csim review can corrupt a good baseline}: on optimize tasks the reviewer may reject and ``fix'' the unmodified, known-correct initial code before the checkpoint anchors (observed once: Qwen3.5 on matmul, latency doubled). The archive should be anchored on the original baseline first; this fix is designed but not yet implemented.
    \item \textbf{No backoff on synth timeout}: repeated synthesis timeouts (Qwen3.5 on vecadd, 4$\times$) are treated like ordinary failures; the agent does not respond by simplifying the design.
    \item \textbf{No HTTP-level retry}: one Qwen3.5 run was lost to an LLM-API read timeout; a retry wrapper and longer default timeout for slow models are needed.
    \item \textbf{Aggressive mode trade-off}: excessive token saving degrades strategy quality (vecadd 1.000$\to$0.737), indicating a token-saving floor.
    \item \textbf{KB not naturally triggered}: across the six tasks, the correctness/synth stages had zero failures (pre-csim review passed first try), so KB retrieval was not exercised. The KB's value will surface on harder hidden tasks; a controlled KB-hit-rate experiment with injected error patterns is planned.
    \item \textbf{Latency variance}: the \texttt{residual} task's final latency varied 10--32 cycles across runs, stemming from LLM strategy-proposal randomness.
    \item \textbf{No \texttt{generate}-type task}: our suite covers repair/structural/optimize only.
\end{enumerate}

\subsection{Future Work}

\begin{itemize}
    \item Anchor the checkpoint archive on the unmodified baseline (fixes the pre-csim corruption mode, App.~\ref{sec:limitations}); add synth-timeout backoff and HTTP-level LLM retry.
    \item Functional-pattern retrieval (\S6.4 of the architecture spec) to reduce optimization variance.
    \item Controlled KB ablation (KB on/off on injected-failure tasks).
    \item Area/power-aware optimization objective if the metric evolves.
    \item Validate generalization on the hidden test set.
\end{itemize}
