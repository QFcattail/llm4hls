## 根因分析 (Root Cause Analysis)

### 1. 为什么没满分：PPA 不可达（latency=0）
- projection_bugfix 是纯组合逻辑，csynth.xml 实测 `Worst-caseLatency=0`、II=1
- harness `scoring.py` 的 `acceleration = base_lat / cand_lat` 前置判断 `if cand_lat and base_lat:`--**0 在 Python 是 falsy**，acceleration 永远 None，`ppa_norm` 恒 0
- agent 的 `_valid_latency()` 也已把 `lat<=0` 当 None（dev-log 2026-07-17-01 已知异常）
- 结论：对这类题，PPA 的 0.3 权重不可达，跑 optimize 只浪费 token/credit。SCORE 1.4 = 2 × (0.5 correct + 0.2 synth + 0.0 ppa) 是 correctness+synth 天花板

### 2. optimize 失败不重试：设计层面不对称
- LLM 选了"Table-based Division with ROM"策略，生成 `div3_table[256]` 但初始化写了 322 个元素（每行 18 个而非 16 个），csim `compile_error`
- `_try_opt_candidate` 在 csim 失败时直接 `return "failed"`，单策略子集直接 `optimize_stop` + break
- correctness（§4.2）和 synth（§4.3）阶段都有 repair 循环（feedback + KB + review 双闸门），**唯独 optimize 没有**--这是设计层面的不对称
- TC-AGENT-003 还把这个 fail-fast 行为 pin 成了预期

### 3. git 历史核查
- `needs_optimize=True` 从第一个 commit（0a84e27, Jul 14）就存在，**不是最近新引入**
- 设计文档 §3.3 也一直说所有题型都跑 optimize
- harness 评分对所有题型统一（repair 题理论上有 PPA 分）
- 结论：用户"按题型跳过"的假设不成立，改用"latency 可达性"判据
