### 3. 论文主要思想摘要

#### 3.1 ReAct（arXiv 2210.03629）——Agent 循环理论基础

**核心思想**：让 LLM 交替进行"推理"(Reasoning) 和"行动"(Acting)。

- **纯推理（如 CoT）的问题**：LLM 闷头想，不与外部世界交互，容易幻觉
- **纯行动的问题**：LLM 盲目调用工具，不思考为什么
- **ReAct 的解法**：Thought → Action → Observation 循环
  - Thought：LLM 推理"现在该干什么、为什么"
  - Action：调用外部工具（如 csim、搜索等）
  - Observation：看工具返回的结果
  - 然后回到 Thought，根据 Observation 决定下一步

**对我们的意义**：agent 主循环的理论基础。每轮让 LLM 先"想"该调用什么工具，
执行后看结果，再"想"下一步。比固定流水线灵活，比盲目试错有方向。

#### 3.2 Anthropic《Building Effective Agents》——Agent 设计模式

**核心思想**：总结了 5 种 agent 架构模式：

1. **Prompt Chaining**：把大任务拆成固定步骤，每步一个 LLM 调用
2. **Routing**：先分类，再路由到不同处理流程
3. **Parallelization**：多个 LLM 调用并行执行，汇总结果
4. **Orchestrator-Worker**：主 agent 分配子任务给多个 worker
5. **Evaluator-Optimizer**：LLM 生成 → 另一个 LLM 评估 → 反馈 → 再生成

**对我们的意义**：最可能用 **Evaluator-Optimizer 模式**——
LLM 生成修复代码 → 工具(csim)评估 → 如果失败，把错误反馈给 LLM → 再生成。
这正是 ReAct 循环的一种具体实现。

文章还强调：**先从最简单的方案开始，需要时再加复杂度**。不要一上来就搞多 agent 编排。

#### 3.3 SWE-agent——成熟的"LLM + 工具循环"参考

**核心思想**：设计了对 LLM 友好的"Agent-Computer Interface"(ACI)。

关键设计原则：
- 工具的输入输出格式要让 LLM 容易理解和生成
- 错误信息要包含足够上下文让 LLM 能自修复
- 限制 LLM 的行动空间（不能什么都能做，容易乱来）

**对我们的意义**：csim/cosim/synth 的调用接口要设计得对 LLM 友好——
返回结构化的错误信息（不只是原始日志），让 LLM 能直接理解问题在哪。

#### 3.4 HLS Repair 论文（arXiv 2407.03889）——直接对应赛题

**核心思想**：针对 HLS C/C++ 代码的常见 bug，用 LLM 自动修复。

方法：
- 识别常见 HLS bug 模式：`+=` 运算符不可综合、bit 宽度不匹配、指针问题等
- 对每种 bug 模式，用 LLM 生成针对性修复
- 检测修复效果：看这些 pattern 的出现频率是否降低

**用户评价**："主要就是拆分步骤，然后有几个约束比如修改 += 运算符、bit 宽度和 Pointer，
然后就完事了。最后检测也是直接找这几个 pattern 的出现频率。"

**对我们的意义**：
- bug 分类方法可参考（编译错/功能 bug/协议错）
- 但我们的 agent 要更通用：不能预设"已知有哪些 bug"，要能自主诊断
- 这篇论文是"规则驱动 + LLM 修"，我们要做"LLM 驱动 + 知识库辅助"

#### 3.5 AutoChip（arXiv 2311.0487）——LLM + EDA 工具反馈迭代

**核心思想**：用 LLM + EDA 工具反馈迭代改进 Verilog 代码（虽然是 RTL 不是 HLS）。

方法：
- LLM 生成代码 → EDA 工具（综合/仿真）反馈错误 → LLM 根据错误修复 → 循环
- 关键：把工具的报错信息精准地传回给 LLM

**对我们的意义**：验证了"工具反馈 → LLM 修复 → 再跑"的循环模式可行。
和我们的 ReAct 循环一致。

#### 3.6 HLSPilot（arXiv 2408.06810）——首个 LLM 驱动全自动 HLS 框架

**核心思想**：C/C++ → HLS 的全自动转换 + 设计空间探索(DSE)。

AMD 案例文章引用了它："HLSPilot combines pattern-guided C-to-HLS transformations
with design-space exploration driven by real compiler reports."

**对我们的意义**：理解 LLM 在 HLS 中的能力边界——能做代码转换、pragma 调优，
但需要工具反馈来驱动。

### 4. AMD LLM4HLS SHA-256 案例文章——方法论核心参考

**这是最重要的参考**。AMD 官方案例，描述了一个完整的 LLM4HLS 优化工作流。

#### 4.1 四阶段工作流（AMD Workflow）

```
┌─────────────────────────────────────────────────────────┐
│                    AMD 四阶段循环                         │
│                                                          │
│  Phase 1: Context Loading（上下文加载）                   │
│  ├── 给 LLM 提供：源码 + 综合报告 + 设备约束               │
│  ├── 包括：latency 分解、II、资源利用率                    │
│  └── 关键：不给综合数据，LLM 只会给泛泛建议                │
│                                                          │
│  Phase 2: Strategy Exploration（策略探索）                 │
│  ├── 让 LLM 提出多个优化策略 + 权衡                        │
│  ├── Prompt 示例："给出综合报告和设备约束，提出多个优化      │
│  │   策略，每个说明延迟收益、资源开销和风险"                 │
│  └── 人（或 agent）从中选一个                              │
│                                                          │
│  Phase 3: Code Generation（代码生成）                      │
│  ├── 让 LLM 生成具体代码修改                               │
│  ├── Prompt 要具体：命名操作、目标、明确不变的部分、         │
│  │   提前标注已知工具陷阱                                   │
│  └── Prompt 示例："合并 generateMsgSchedule 和             │
│  │   PreProcessing 为单个函数。不要修改其他函数调用。        │
│  │   注意 dataflow 冲突和非法连接。"                        │
│                                                          │
│  Phase 4: Synthesis, Simulation, Validate（验证）         │
│  ├── 跑 HLS 综合和协同仿真                                 │
│  ├── 如果报错，把错误信息变成下一轮 prompt：                │
│  │   "综合报告错误 [XFORM 203-313] 和 [RTGEN 206-102]。    │
│  │   修复冲突。"                                           │
│  └── LLM 诊断错误 → 生成修复 → 再综合 → 循环              │
│                                                          │
│  循环通常 2-3 轮收敛                                       │
└─────────────────────────────────────────────────────────┘
```

#### 4.2 LLM 的优势与不足（AMD 文章总结）

**LLM 擅长的**：
- **架构模式识别**：能识别 DATAFLOW 反模式（不能重叠的阶段间用 FIFO）
- **设计空间探索**：快速列出多个优化策略 + 量化分析每个的可行性
- **代码生成**：~80% 首次正确率（结构正确，stream 接口/loop 标签/pragma 放置正确）

**LLM 不擅长的（需要知识库/人工补救）**：
1. **Pragma 交互规则**：在同一层级同时用 PIPELINE 和 DATAFLOW（违规）
2. **重构后的死代码**：合并函数后留了无人消费的 stream → illegal connection
3. **算法边界条件**：消息填充路径需要人工验证

> AMD 原文："these gaps could be further mitigated by pairing the LLM with
> domain-specific agents or retrieval-augmented skills backed by an HLS
> knowledge base covering pragma constraints, common refactoring pitfalls,
> and tool-specific error patterns."

**这正是我们要做的**：建知识库覆盖这些 LLM 短板。

#### 4.3 有效 Prompt 策略（AMD 文章总结）

1. **角色设定**："You are a senior Vitis HLS engineer and FPGA hardware architect"
2. **务必同时给源码 + 综合报告**：有数据比没数据建议精准得多
3. **要求多策略再选**：让人/agent 做选择，LLM 做生成
4. **明确不变的部分**："do not modify other function calls"、"keep top-level interface unchanged"
5. **报错时给具体错误码**：`[XFORM 203-313]` 比模糊描述精准得多

#### 4.4 实验结果

- SHA-256 kernel，Vitis HLS 2025.2，UltraScale+ xcu200
- 基线：880 cycles，4.027ns clock，3.54µs 执行时间
- 优化后：426 cycles，3.739ns clock，1.59µs 执行时间
- **2.22× 加速，52% 延迟降低**，2 周完成
- LLM 贡献约 60%（架构推理 + 代码生成），人工贡献约 40%（验证 + 调试 + 决策）
- 资源：LUT 从 0.69% → 1.63%，FF 从 0.58% → 0.97%（远未饱和）

### 5. 架构思考（待明天细化）

读完论文后浮现的架构问题（不是最终设计，是需要想清楚的点）：

#### Q1: 固定流水线 vs LLM 自主决策？
- 固定流水线：csim → 修 → csim → csynth → cosim（简单但不灵活）
- LLM 自主：LLM 看状态决定下一步调什么工具（灵活但费 token）
- 倾向：**混合**——大框架固定（先 correctness 后 PPA），每步内 LLM 自主

#### Q2: 知识库形态？
- 不是 wiki/搜索引擎，而是结构化数据（dict/JSON）+ 简单匹配
- 每条：error_code + symptom + root_cause + fix + example
- 检索方式：先字符串匹配错误码，量大了再考虑 embedding

#### Q3: 知识库注入时机？
- 正常时不注入（省 token）
- 解析到特定错误码时才注入对应修法

#### Q4: LLM 输出解析？
- 要求 LLM 返回结构化格式（JSON 或 XML 标签包裹代码块）

#### Q5: 预算分配？
- csim 便宜先跑、synth 中等、cosim 最贵最后跑
- 超预算优雅终止，交当前最佳代码
