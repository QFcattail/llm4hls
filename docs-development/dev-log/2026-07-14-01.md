### 5. 深度架构讨论（核心）

用户提出架构设想（路由器 → 概要设计 → 详细设计 → 原生编写 HLS → 调试 → 优化，每步双 agent review）。通过逐项对照 harness 真实题目 + AMD 案例，识别并修正多个误解：

#### 5.1 澄清的概念误解
- **输入永远是 HLS C++ kernel**（不是纯 C），header 锁死签名。"路由器判断 C 还是 HLS"不成立，改为按 task_type 路由。
- **credit vs token 是两套预算**：credit 是硬限制（超了停），token 是软限制（影响分）。用户一度混为一谈，讲清后用户明白"省 credit 无奖励，省 token 才有价值"。
- **"跳过低级关卡"不成立**：评分用 hidden testbench（不花 agent credit）照样验所有关卡；且改高级 bug 会破坏低级正确性，必须回溯重验。
- **"错误≥3 就重写"不成立**：credit 约束下重写易破产（一次重写验证 5-25 credits，repair 题预算仅 20）。
- **"每步双 agent review"过度**：token 翻倍；review 只在关键决策点做。
- **"白盒检查/逻辑推演"用错地方**：AMD 明确这是 LLM 短板；验证应靠 csim/synth/cosim 跑，不靠 LLM 想。

#### 5.2 用户独立推演出的正确洞察（值得记录）
- **存档/检查点模式**：用户自己推出"初始存档、通过就存、提交最新存档而非最后改动"——与官方 ReferenceAgent 的 `best` 变量逻辑一字不差。
- **存档判定两规则**：① 关卡数更多则存；② 关卡数相同则比 latency，快的存。补全第三条：③ 关卡数更少绝不存（correctness 倒退）。
- **速度数据的来源**：用户问"速度是不是 synth 才有"——正确。csim 不返回 latency，synth/cosim 才返回。

#### 5.3 线性流程之争的澄清
用户坚持"线性流程走哪算哪"，质疑我说的"budget 决策树"。经深入辩论，**用户是对的**：
- credit 维度上，线性流程与任何"聪明止损"拿到相同分数（省 credit 无奖励）。
- 真正需要权衡的是 token 维度，而那靠"让每步更可能一次过"（减少重试），不靠"决定何时停"。
- **修正：主流程是线性的（correct → synth → optimize），每次改代码后回溯重验已通过关卡，存档机制天然提供回滚。唯一分支点是 structural 题多一道 cosim 关卡。**
