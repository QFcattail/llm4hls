# 项目工程规范 (Project Engineering Conventions)

> 本文档提炼自一个成功交付的多子系统嵌入式工程项目，定义了一套"人机协作、文档驱动、
> 可追溯"的工程规范。目标是：**即使开发者中途更换，接手的人也能零压力地看懂
> "现在做到哪一步、为什么这么设计、接下来要做什么"**。
>
> This document captures the engineering conventions from a successfully delivered
> multi-subsystem embedded project. The goal: **a new developer can take over
> mid-stream and understand "where we are, why it's designed this way, and what
> comes next" without asking anyone.**

| 项目 | 内容 |
|---|---|
| 文档版本 | v1.0（本项目采用，唯一差异：代码注释风格用 Google style 而非 Javadoc） |
| 适用范围 | LLM4HLS Agent 项目（Python 单子系统 + 官方 harness 复用） |
| 核心理念 | 文档是进度的唯一真相来源；AI 负责执行，人类负责决策 |

## 1. 核心理念

### 1.1 三条铁律

1. **文档是进度的唯一真相来源 (Single Source of Truth)**
   - 任何人想知道"现在做到哪一步、接下来做什么"，只需要看 `engineering-plan.md` 一份文档。
   - 代码会说谎（注释过期、分支未合并），但维护良好的工程计划不会。

2. **每个阶段都需要评审通过才能进入下一阶段 (Stage Gate)**
   - 需求 -> 设计 -> 测试用例 -> 编码 -> 测试 -> 总结，每一步都有"闸门"。
   - AI 不擅自推进阶段，必须等人类确认。

3. **如果开发者某天突然中断，另一个人能零压力接手 (Bus Factor = ∞)**
   - 这一条是所有规范的终极目标。日志告诉你"为什么"，计划告诉你"是什么"。

### 1.2 为什么有效

这套规范在真实项目中经受了考验：一个包含 5 个子系统（ESP32 固件 / Node.js 中转服务器 / Flutter 手机 App / Flutter 桌面 Agent / 辅助工具）、跨 4 种编程语言（C / Dart / JavaScript / Python）、经 30+ 次开发会话从零交付到端到端验证通过的项目，全程由 AI 编码 + 人类决策的协作模式完成。成功的关键不是某个工具，而是：

- **原子任务拆解**：不写"今天做固件"，而是写"P4-18 WebSocket 隧道客户端骨架 + 帧解析"。
- **实时文档同步**：每完成一个原子任务立刻更新工程计划和开发日志，不攒到一天结束。
- **约束前置**：把"踩过的坑"写成硬约束文档，动手前先读，避免重复踩坑。

本项目（fpga-agent）将其单子简化为单子系统 Python 项目，但铁律不变。

## 2. 仓库目录结构

### 2.1 顶层目录设计原则

每个顶层目录只承担**一个职责**（"单一职责原则"在目录层面的体现）：

```
project-root/
├── docs-overview/        项目介绍、总体架构、术语表（所有人 first read）
├── docs-development/     工程过程文档（需求、设计、计划、日志、评审、测试、技术债）
│   ├── requirements/     需求分析
│   ├── design/           详细设计（按子系统拆分）
│   ├── engineering-plan/ 工程计划（进度唯一真相来源）
│   ├── dev-log/          开发日志（按日期）
│   ├── reviews/          评审记录
│   ├── test-plan/        测试用例
│   └── internal-notes/   技术债清单、踩坑笔记（仅开发者自己）
├── <subsystem-1>/        子系统 1 代码
├── <subsystem-2>/        子系统 2 代码
├── ...
├── tools/                辅助工具（日志服务、脚本等）
├── README.md             项目总入口（含架构图、快速开始、阅读路线）
└── .gitignore
```

本项目的实际目录映射：`agent/`（Agent 本体）、`tui/`（TUI 仪表盘）、`scripts/`（CLI 入口）、`contest/`（官方 harness + 赛题材料）、`tools/`（辅助脚本）、`runs/`（运行产物）。

### 2.2 命名规范

- **顶层目录**：英文小写 + 连字符（kebab-case），如 `agent`、`contest`、`tools`。
  - 原因：避免中文路径在跨平台工具链（尤其 Windows / ESP-IDF）中引发编码问题。
- **文档文件**：英文小写 + 连字符，如 `engineering-plan.md`、`tech-debt.md`。
- **开发日志**：`YYYY-MM-DD-<序号>.md`，如 `2026-07-09-02.md`（同一天第二次会话）。
- **评审记录**：`YYYY-MM-DD-<阶段>-review.md`，如 `2026-07-02-design-review.md`。
- **Python 包目录**：用下划线（`knowledge_base`），因为必须是合法 Python 标识符；纯文档目录可用连字符（`knowledge-base`）。

### 2.3 双层文档体系

| 层 | 目录 | 面向 | 内容 | 语言 |
|---|---|---|---|---|
| **概览层** | `docs-overview/` | 所有人，尤其新手 | 项目背景、总体架构、术语表、阅读地图 | `.md`（英文）+ `.cn.md`（中文） |
| **开发层** | `docs-development/` | 开发者、接手者 | 需求、设计、计划、日志、评审、测试、技术债 | 设计文档双语；日志/评审等中文为主 |

### 2.4 代码配套文档

- 每一个代码子目录都需要一份 `README.md`（英文）+ `README.cn.md`（中文），包含：文件清单、调用链（mermaid 图）、知识点、构建方法、已知坑点。
- 每一个代码文件（或每一组紧密相关的文件）都需要一份 `<同名>.doc.md` 配套说明文档，采用**中英双语**：先中文说明，后附英文翻译。
- 代码子目录的 README 是"新手引导"，让人不需要问任何人就能理解该子系统的实现。

## 3. 软件工程流程 SDLC

### 3.1 阶段划分

项目严格按以下顺序推进，**每个阶段结束都需要用户/评审确认后才能进入下一阶段**：

```
需求分析 (Requirements)
    ↓ 评审通过
详细设计 (Detailed Design)
    ↓ 评审通过
测试用例编写 (Test Case Writing)
    ↓
编码实现 (Implementation)
    ↓
按用例测试 (Testing)
    ↓
总结文档/README (Summary & README)
```

### 3.2 阶段编号与状态

每个阶段编号为 `P<数字>`，状态用 emoji 标注：

| 图例 | 含义 |
|---|---|
| ⚪ | 未开始 |
| 🟡 | 进行中 |
| 🟢 | 已完成 |
| 🔴 | 阻塞 |

### 3.3 阶段闸门规则

- 需求分析和详细设计都要写到"**细到不能再细**"，并经过评审（记录在 `reviews/`）。
- 测试用例在详细设计完成后就要写好，覆盖所有功能点和所有交互按钮。
- 纯 GUI 才能验证的部分如果没有自动化手段，在用例中明确标注"人工验证 (M)"，**不假装能自动化测试**。
- 每完成一个阶段/一个原子任务，执行一次 git 提交。

### 3.4 什么时候细化任务

**每进入一个新阶段时，先细化该阶段的原子任务**。不要在项目一开始就把所有阶段的任务都列出来——后面的任务依赖前面的成果，提前细化会大量返工。例如：

- P0 阶段开始时，只细化 P0 的原子任务。
- P2（详细设计）阶段开始时，把"详细设计"拆解成每个子系统的设计文档任务。
- P4（实现）阶段开始时，按子系统拆解编码任务。

## 4. 工程计划与原子任务

### 4.1 核心原则

进度管理的核心原则：**计划文档里不能只写"今天要做什么"，必须能让人一眼看到"整个项目被拆成了哪些原子任务、每个任务目前是什么状态"**。

### 4.2 文档结构

`engineering-plan/engineering-plan.md` 包含以下部分：

1. **里程碑总览表**：所有阶段（P0-Pn）的名称、状态、说明。
2. **当前阶段详情**：现在在哪、下一步做什么。
3. **原子任务清单**：按阶段分组的任务表，每个任务一行。
4. **里程碑依赖与阻塞点**：外部依赖（硬件、环境、设计图）的状态和影响。
5. **变更记录**：时间 + 变更内容，每次更新追加一行。

### 4.3 原子任务规范

- **编号规则**：`P<阶段号>-<序号>`，如 `P4-18`。
- **粒度要求**：一个原子任务应该能在一次开发会话（几小时内）完成。如果一个任务需要一周的量，说明它不够原子，需要继续拆。
- **任务表字段**：任务ID | 任务描述 | 状态 | 产出物。
- **状态变更**：完成一个任务立刻改状态，并在"变更记录"追加一行。**不要等到一天结束才批量更新**。

### 4.4 更新时机

> 每完成一个原子任务，立刻把对应行的状态改掉，并在"变更记录"里追加一行。

这是整个规范中最重要的操作纪律。延迟更新会导致工程计划与现实脱节，失去"唯一真相来源"的价值。

## 5. 开发日志规范

### 5.1 作用

`engineering-plan.md` 告诉你**现在的状态**（哪些任务完成了、哪些没完成）。
开发日志告诉你**为什么会是这个状态**（做了什么决策、踩了什么坑、为什么这么设计）。

### 5.2 文件命名

`YYYY-MM-DD-<序号>.md`，同一天有多次会话时用序号区分（`01`、`02`、`03`...）。

### 5.3 日志模板

每篇日志包含以下字段（参考大厂"工程日志 Engineering Log"格式）：

```markdown
# 开发日志 YYYY-MM-DD-NN

## 基本信息 (Meta)
- 日期 (Date):
- 参与者 (Participants):
- 所处阶段 (Phase): 对应 engineering-plan.md 中的阶段编号

## 本次目标 (Goal of This Session)
简述本次会话打算完成什么。

## 完成的工作 (What Was Done)
- 逐条列出实际完成的原子任务，附对应 engineering-plan.md 中的任务ID
- 涉及的关键决策和理由

## 遇到的问题与解决方案 (Issues & Resolutions)
- 问题描述
- 排查过程（简述即可，细节可放 internal-notes/）
- 最终解决方案 / 或标注为待解决

## 未完成 / 下一步 (Unfinished / Next Steps)
- 列出本次没做完、留给下次的事情
- 对应 engineering-plan.md 中状态仍为"进行中"或"未开始"的任务ID

## 相关提交 (Related Commits)
- commit hash + 简述

## 需要用户确认的事项 (Needs User Confirmation)
- 如果有需要用户决策/确认才能继续的事项，列在这里
```

### 5.4 写作纪律

- **每完成一段实质工作，立刻补日志**，不要攒。
- 排查问题的过程可以简述，细节放 `internal-notes/`，日志只记结论。
- 如果一篇日志纠正了前一篇日志的结论，在**前一篇顶部加纠正指向**，新篇详细说明正确结论和原因。不要悄悄改旧日志。
- 日志里引用代码位置用 `文件名:行号` 格式，方便点击跳转。

## 6. 评审机制

### 6.1 评审记录

每次评审（需求评审、设计评审、测试用例评审）都记录在 `reviews/` 下，命名格式 `YYYY-MM-DD-<阶段>-review.md`。

### 6.2 评审记录模板

```markdown
# <文档名称> 评审记录 第N轮

## 基本信息
- 评审对象 (Reviewed Document):
- 评审时间 (Date):
- 评审人 (Reviewer):

## 评审意见 (Comments)
| 编号 | 位置 | 意见 | 处理方式 | 状态 |
|---|---|---|---|---|
| 1 | ... | ... | ... | 已修订/待讨论/不采纳(原因) |

## 结论 (Conclusion)
- [ ] 通过，可进入下一阶段
- [ ] 需修订后再次评审
```

### 6.3 评审的实质

评审不是走过场。在真实项目中，设计评审发现了 5 处调用链断点（119 个事件中逐条核对发现的），用户反馈"函数缺少前置 I/O 描述"，最终补充了 I/O 速查表和触发方标注。**评审是质量的关键防线**。

## 7. 技术债管理

### 7.1 技术债清单

> 注：`internal-notes/` 目录已从开源版本移除，以下流程描述保留供参考。

`internal-notes/tech-debt.md` 汇总项目当前已知的技术债，每条包含：

- **编号**：`TD-<序号>`（如 `TD-07`）
- **位置**：精确到文件和行号
- **现象**：具体表现
- **影响**：对用户/系统的影响
- **来源**：对应的 dev-log
- **修复方向**：建议的解决方案
- **状态**：未修复 / ✅ 已修复（标注日期）

### 7.2 分级

按严重程度分级：

| 级别 | 含义 |
|---|---|
| **Critical** | 影响安全或核心功能正确性 |
| **High** | 影响功能可靠性，已知会复现的 bug |
| **Medium** | 影响体验或边缘场景 |
| **Low** | 文档/规范类 |

### 7.3 修复后处理

修复一条技术债后：
1. 在该条目后加 `✅ 已修复（日期）`。
2. 在 dev-log 中记录修复过程。
3. 不要删除历史描述——保留"曾经是什么问题、怎么修的"供后人参考。

### 7.4 internal-notes 与 dev-log 的区别

| 目录 | 性质 | 内容 |
|---|---|---|
| `dev-log/` | 面向所有人的正式日志 | 结论性记录：做了什么、结果是什么 |
| `internal-notes/` | 仅开发者自己 | 过程性草稿：走过的弯路、临时命令、不成熟的想法 |

## 8. 文档规范

### 8.1 语言约定

| 文档类型 | 语言 |
|---|---|
| 面向外部用户的文档（README、getting-started、design、experiments、子系统 README） | **`.md`（英文）+ `.cn.md`（中文）双文件**，互相跳转链接 |
| 代码配套文档（`.doc.md`） | **中英双语**：先中文，后英文翻译（内联，不拆分） |
| 内部过程文档（dev-log、requirements、reviews、test-plan） | **中文为主**，关键术语标注英文 |
| 代码注释 | **纯 ASCII 英文**（见 §9） |

**双文件规范**：
- `.md` 为英文主文件（外部链接默认指向它）。
- `.cn.md` 为中文镜像文件。
- 每个文件顶部必须有跳转链接：英文版顶部 `> [中文](<文件名>.cn.md)`，中文版顶部 `> [English](<文件名>.md)`。
- 两文件内容保持同步，修改一处必须同步另一处。

### 8.2 设计文档规范

- 设计文档**不包含代码**，用文字描述行为、状态、字段、流程。
- 详细到"细到不能再细"，让接手的人能照着重现。
- 关键术语中英对照。
- 设计文档描述"应该怎么实现"，与代码实现可能存在差异——**以代码为准**，差异在 design README 中列出。

### 8.3 测试用例规范

- **用户行为视角**：只描述 Given（前置条件）/ When（用户动作）/ Then（可观察反馈），不描述内部实现。
- **覆盖维度**：每个功能至少覆盖 Happy Path / 错误异常 / 重试恢复 / Monkey 乱点。
- **可自动化性标注**：A（可自动化）/ M（必须人工）/ S（半自动）。
- **编号规则**：`TC-<子系统>-<三位序号>`，如 `TC-AGT-001`。
- **可追溯性**：每条用例标注对应需求 ID 和设计章节。

### 8.4 需求分析文档结构

需求分析文档应包含以下章节：

1. 项目概述（一句话定义、背景动机、目标、范围）
2. 用户角色与画像
3. 用户故事（完整操作流程，建立直觉）
4. 功能需求（每条有唯一编号 `REQ-<子系统>-<序号>`）
5. 非功能需求（性能、可靠性、易用性）
6. 边界与非目标（**很重要**：明确列出"故意不做的事"）
7. 验收标准
8. 风险与依赖
9. 开放问题（需要决策但尚未确定的事项，决议后记录）

### 8.5 图表规范

- 流程图、架构图、状态机用 **mermaid**（GitHub/Markdown 原生渲染）。
- 不用纯文本"画"结构图（跨平台显示不一致）。
- 复杂时序用表格逐事件核对（参考设计评审附录 A 的事件覆盖验证）。

## 9. 代码规范

### 9.1 注释风格

> **本项目与原规范的唯一差异：采用 Google style 而非 Javadoc。**

- 所有代码注释使用 **Google style** docstring：模块/类/函数上方用三引号字符串 `"""..."""`，用 `Args:`、`Returns:`、`Raises:`、`Attributes:` 等段落标签。
- **统一采用这种风格**，不混用 Javadoc `@param`/`@return` 或 Sphinx `:param:` 风格。

示例（Python）：

```python
def route(task) -> RunPlan:
    """Build a RunPlan from a llm4hls.Task.

    Args:
        task: A harness Task object exposing ``.type`` and ``.requires_cosim``.

    Returns:
        A RunPlan describing the correctness gate, optimization entry, and
        initial checkpoint level for the task.
    """
```

### 9.2 注释语言

- **所有代码注释必须是纯 ASCII 英文**，不允许出现中文字符或其他非 ASCII 符号。
- 原因：跨平台（尤其 Windows 端、ESP-IDF 工具链）对非 ASCII 字符编码处理不一致，会导致编译失败或乱码。这是**血泪教训**换来的硬约束。
- 常见违规：em-dash `—`（用 `--` 代替）、`§`（用 `section` 代替）、`•`（用 `-` 代替）、`≈`（用 `~` 代替）、中文标点（用对应 ASCII 标点代替）。

### 9.3 配套文档

- 每个代码文件配一份 `<同名>.doc.md`，中英双语，说明用途、关键函数、导出、依赖。

## 10. 运行环境约束

### 10.1 为什么需要这份文档

> 本文档记录各机器/设备的硬性约束。**违反这些约束会导致卡死或返工**，
> 任何 AI/人在动手前必须先读这份。

### 10.2 内容

`runtime-constraints.md`（内部文档，不含于开源版）记录：

1. **机器与设备归属**：哪台机器干什么、怎么连、有什么权限、有什么限制。
2. **端口与防火墙**：哪些端口已放行、新增端口的操作步骤。
3. **环境限制**：如 Vitis 版本限制、Python 版本要求、磁盘空间限制。
4. **AI 操作约束**：动手前先读文档、写日志、不擅自动手前先确认。
5. **版本号与界面截图**：见 §11。

### 10.3 核心原则

- **没做之前先读**：动手前先读需求、设计、约束、最新 dev-log，不要基于假设操作。
- 踩过的坑要写成约束，让后来者不重复踩。

## 11. 版本号管理

### 11.1 硬约束

**所有带界面的子项目，每次重新构建/部署前必须 bump 版本号**，否则用户和 AI 无法从界面辨认"跑的是新版还是旧版"。

> 曾因没 bump 版本号，把旧二进制当成最新版排查了一整轮。

### 11.2 Bump 规则

| 改动类型 | bump 幅度 |
|---|---|
| 修了影响运行时行为的代码 | 至少 patch +1 |
| 新功能 | minor +1 |
| 仅文档/注释 | 可不 bump |

本项目版本号定义在 `agent/_version.py` 的 `__version__`，语义化版本（SemVer）格式 `MAJOR.MINOR.PATCH`。

### 11.3 界面显示版本号

所有带界面的子系统**必须**在界面上显示版本号。这不是可选项——当排查问题时，版本号是确认"跑的是哪个版本"的唯一可靠途径。本项目的 TUI 仪表盘标题栏显示版本号。

## 12. 人机协作模型

### 12.1 分工

| 角色 | 职责 |
|---|---|
| **人类（项目负责人）** | 立项、技术决策、需求评审、阶段闸门确认、现场物理操作（服务器部署、Vitis 安装、截图） |
| **AI（开发助手）** | 技术调研、编码、文档撰写、开发日志记录、测试编写 |

### 12.2 AI 操作纪律

1. **不擅自推进阶段**：P1 评审没过，不偷偷开始 P2。
2. **不擅自做约束类决策**：网络端口、安全降级、设备归属等，先和人类确认。
3. **实时记录**：每完成一段实质工作立刻补 dev-log。
4. **动手前先读**：读需求、设计、约束、最新日志，不基于假设操作。
5. **状态变更后验证**：GUI 状态变更后截图确认实际渲染，不只靠日志推断。

### 12.3 为什么这套模型有效

- 人类聚焦高价值决策（做什么、为什么），AI 聚焦高吞吐执行（怎么做、写文档）。
- 文档是两者的"共享记忆"——人类不需要记住所有细节，AI 不需要重新理解上下文。
- 阶段闸门防止 AI 跑偏（"我觉得需求差不多够了，直接开始设计吧"——不行，必须等评审）。

## 13. Git 提交规范

### 13.1 提交时机

- 每完成一个原子任务即提交，不要攒一大批改动一次提交。
- 每个阶段结束提交一次里程碑。

### 13.2 提交信息格式

采用 Conventional Commits 风格，带子系统 scope：

```
<type>(<scope>): <简述>

<可选正文>
```

| type | 含义 |
|---|---|
| `feat` | 新功能 |
| `fix` | bug 修复 |
| `docs` | 文档变更 |
| `refactor` | 重构（不改功能） |
| `perf` | 性能优化 |
| `chore` | 杂项（版本号 bump、依赖更新） |

scope 用子系统名：`agent` / `tui` / `tools` / `contest` / `dev-log`。

示例：
```
feat(agent): implement correctness stage repair loop
fix(tui): resolve black screen on two App conflict
docs(dev-log): 2026-07-17-01 TUI dashboard + 9 bug fixes
chore: bump version to 0.1.1 for TUI release
```

### 13.3 推送

每次提交后推送到远程仓库，保证备份和协作可见性。
