## 需求分析文档结构

一份完整的需求分析文档应包含：

1. **项目概述** - 一句话定义、背景动机、目标、范围
2. **用户角色与画像** - 谁会用、怎么用（本项目：赛事评审 + Agent 开发者）
3. **用户故事** - 完整操作流程，建立直觉（agent 端到端修复 HLS 代码的 6 步流程）
4. **功能需求** - 每条有唯一编号 `REQ-<子系统>-<序号>`（如 `REQ-AGT-01`）
5. **非功能需求** - 性能（token 消耗）、可靠性（预算内止损）、易用性（TUI 可观测）
6. **边界与非目标** - **很重要**：明确列出"故意不做的事"（如不实现 RTL 级优化、不做 Verilog 修复）
7. **验收标准** - 每条需求怎么算"做完了"（对应评分公式 SCORE > 0）
8. **风险与依赖** - 哪些事情可能出问题（Vitis 环境部署、API key、隐藏测试集）
9. **开放问题** - 需要决策但尚未确定的事项，决议后记录

## 评审

需求分析完成后，提交评审（记录在 [`../reviews/`](../reviews/)），通过后方可进入 P2 详细设计。
